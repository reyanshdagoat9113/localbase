LocalBase landing — plan

Ship a production static site from this repo to localbase.reylabs.in, using the same Railway + reylabs.in setup as DevDesk.

Branch: dev Package: packages/landing Status: code local / not deployed

1. Context (what was decided)

LocalBase is a local CLI (npx @localbase/cli init), not a hosted backend. A marketing site is not a launch gate for private beta, but it is worth building now because a domain and Railway are already in place.

Constraints that are already locked:

  • Build the site in this repo, not in DevDesk.
  • Tune it and make it production-ready (SEO, health check, static server).
  • Deploy on Railway to localbase.reylabs.in.
  • The apex domain reylabs.in is on Namecheap.
  • Do not host the LocalBase runtime. This service is the marketing site only.
  • Do not fold LocalBase into devdesk.reylabs.in.

Recommended Railway shape

A new project named LocalBase, not a new environment on Devdesk. Environments clone every service in a project. Devdesk currently only has @devdesk/landing. A second project (or, if you insist on one project, a second service) is the right model.

A — recommended New Railway project LocalBase, one landing service, domain localbase.reylabs.in.
B — acceptable New service @localbase/landing inside the existing Devdesk project. Both sites share one project/billing; names stay mixed.
C — not recommended New environment on Devdesk. It clones DevDesk’s landing into that environment. Wrong product coupling.

3. What still needs to be done

Step 1 — Review and commit

  1. Look at the page (npm run landing:dev).
  2. Commit packages/landing/, root package.json, and package-lock.json.
  3. Push dev (or open a PR). GitHub-connected Railway deploys need this on the remote.

Step 2 — Railway (blocked until confirmed)

Create project LocalBase (choice A), one service, root directory packages/landing:

  • Build: npm run build
  • Start: npm start
  • Health: /healthz
  • Build-time variable: VITE_SITE_URL=https://localbase.reylabs.in (then redeploy)
  • Generate a *.up.railway.app domain, then attach localbase.reylabs.in

Isolated subdirectory deploy matches DevDesk: Railway root directory /packages/landing. The landing package is self-contained and does not depend on other workspace packages at runtime.

Step 3 — Namecheap (reylabs.in)

After Railway prints DNS records:

  • CNAME host localbase → the target Railway gives (often *.up.railway.app or ghs.railway.app)
  • Wait for TLS / domain VERIFIED

This step cannot be done from this machine. Namecheap is yours.

Step 4 — Prove production

  • /healthz on the Railway domain
  • Site loads on https://localbase.reylabs.in
  • Install copy, GitHub/npm links, screenshots, theme toggle, FAQ
  • OG / canonical URLs use https://localbase.reylabs.in
  • Optional later: point package homepage fields at the domain

Step 5 — Optional polish (not required to go live)

  • GitHub auto-deploy from dev or main after the first deploy
  • A CI job that only typechecks/builds landing (today it rides along with root npm run build --workspaces)
  • Homepage links on @localbase/* packages once the domain is live

4. What is needed from you

  1. Railway topology — pick A, B, or C (A recommended).
  2. Permission to mutate Railway. Creating a project or service was blocked last time. Explicit yes to create + deploy.
  3. DNS. After the domain is attached, you add the CNAME in Namecheap. You will get the exact host/value.
  4. Git. Confirm whether to commit and push (needed for GitHub-connected deploys). A railway up from packages/landing can ship without a push if the CLI is installed.
  5. CLI vs MCP. railway is not on this machine. Either install the CLI, or deploy through Railway MCP once create is approved.

5. Sequence after approval

  1. Commit (and push if GitHub deploys are wanted).
  2. Create the Railway project/service as chosen in section 4.
  3. Deploy packages/landing, set VITE_SITE_URL, confirm /healthz.
  4. Attach localbase.reylabs.in and send the Namecheap record.
  5. You add DNS; wait for verify; check the live site.

6. Out of scope for this plan

  • Hosting LocalBase itself (API / Studio) on Railway
  • Private beta, npm latest promotion, or the public go decision
  • PostgreSQL or production-backend positioning
  • A docs portal, waitlist, or blog
